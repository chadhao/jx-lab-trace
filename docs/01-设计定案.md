## 1. 业务背景与范围

### 1.1 业务模式

- **受托加工为主**：原料由**客户发来**，加工完成后**客户提走**，**物流由客户负责**（客户提前告知车辆信息）。
- **预留自购模式**：不排除后期自购原料加工后直接销售成品 ⇒ 用「业务类型」字段区分，**编入追踪码**。
- 原料为**吨袋包装**；**收货、投料等一切操作的最小单位都是吨袋**。

### 1.2 要解决的问题

原料从**收货 → 生产中间样 → 成品**全过程的检测数据可追踪，做到：

1. **正向追溯**：某车/某袋原料，流向了哪些成品批、哪些客户；
2. **反向追溯**：某批成品，用了哪些车/哪些袋的原料、当时检测结果如何；
3. **检测数据可信**：谁在什么时候、用什么方法、测出了什么、有没有改过。

### 1.3 一期范围（见 §9 分期）

收货预报 → 过磅 → 打码贴标 → 扫码取样 → 检测录入 → 生产投料 → 成品出场 → **追溯查询 → 对外报告分享**。

### 1.4 明确不做（本期）

| 项 | 理由 |
|---|---|
| 仪器数据直连自动采集 | 二期；前置条件是先查清各仪器是否有导出能力 |
| 离线作业与断网同步 | 磅房与化验室已有 VLAN30 网络（2.5G），无此约束 |
| 盲样检测 | 用户明确不需要 |
| 链接访问隔离 | 用户明确定案「不做隔离、可随意转发」 |
| 与采购审批平台的数据接口 | 一期零接口；口径对齐即可 |
| 生产工序节点维度 | 生产过程中只有一个取样点 |

## 2. 设计原则（贯穿全系统）

### P1 · 数据不可变：只追加，不改行

**删除与修改统一为「作废 + 新增」**：所有业务表**只 INSERT 与标记失效**，**从不 UPDATE 关键字段**。要修正 ⇒ 原行盖失效戳 + 插新行 + 互相记 `supersedes / superseded_by`。

- 代价：查询需带 `is_current = 1` 条件。
- 收益：审计追踪天然成立，「当时测的是多少」永远可回溯。

### P2 · 码携带「身份」，关系存库

追踪码只表达**「这是谁」**（哪个客户、哪个物料、哪一天的哪一车/哪一袋），**不表达「它流向谁」**。
多对多的谱系（投料关系、成品来源）**只能存关系表** —— 任何试图把谱系编进定长码的设计都会失效。

### P3 · 校验的是「声明」，不是「事实」之外的东西

码里有校验位、有版本位，**目的只是防手输错与格式自检**，**不防伪造**。防伪造靠权限与审计。

### P4 · 报表层与业务层解耦

报表/看板是**独立模块**：**只读业务表、绝不写业务表**，可单独替换与调整，不影响核心表结构与录入流程。

## 3. 术语与对象模型

```
客户 customer
   │
   └─ 预报单 arrival_notice ──→ 车次 truck_lot（到货事件）
                                    │
                                    ├─ 吨袋 bag ×N          ← 操作最小单位
                                    │     └─ 原料样 sample（扫吨袋码取样）
                                    │
                                    └─ 投料 feed_record ×N ──┐
                                                             ↓
                                              生产批 production_batch
                                                ├─ 作业段 batch_operation ×N（班组/时间）
                                                ├─ 中间样 sample
                                                └─ 成品批 fg_lot
                                                      ├─ 成品袋 fg_bag ×N
                                                      ├─ 成品样 sample
                                                      └─ 出货 shipment ──→ 客户
```

| 对象 | 说明 | 关键点 |
|---|---|---|
| **客户** | 委托方 | 4 位数字编号，全局唯一 |
| **物料** | 原料/成品统一建模 | 由「原料组成 × 原料类型」两个维度组合而成 |
| **车辆** | 车牌号主数据 | 长期存在，记录常用司机/电话 |
| **预报单** | 客户提前告知的车辆信息 | 由收货员录入 |
| **车次** | 一次到货事件 | ★ 同一辆车一天来两趟 = 两个车次 |
| **吨袋** | 车内的一袋原料 | ★ 收货/投料的最小单位，逐袋贴码 |
| **生产批** | 一次投料产出 | 可跨班组（记多段作业）；可多车合并 |
| **成品批** | 生产批的产出 | 可拆分为多批 |
| **成品袋** | 成品吨袋 | 出场逐袋扫码 |
| **样品** | 原料样/中间样/成品样 | 留样是一等公民，管位置与期限 |

### 3.1 谱系关系（多对多，存库不存码）

- **车次 ⇄ 生产批**：**N:M**（一车可拆多批、多车可并入一批）
- **生产批 → 成品批**：1:N
- **成品批 → 出货**：N:M

### 3.2 称重口径（重要限制）

**只有地磅称整车，不逐袋过磅**。

- `车次` 记 **毛重 / 皮重 / 净重**；
- `吨袋` 的重量 = **车净重 ÷ 袋数**，即 **摊算值**；
- ★ **系统必须显式标记 `weight_is_allocated = true`**，追溯报告写作「**约 X 吨**」。

> 理由：客户日后追问「这袋料到底多少吨」，必须答得出这个数**来自摊算而非实测**。不标记的话，半年后无人记得它是估的。

## 4. 追踪码规则

### 4.1 方案选型

采用 **「结构化 + 编码版本位 + 校验位」**（方案丙）。核心取舍：

| | 甲 纯结构化 | 乙 短流水 | **丙 结构化+版本位（选定）** |
|---|---|---|---|
| 编码体系变更（客户/物料重编号、增删层级） | ★ 存量标签全废 | 不受影响 | ★ **老码按版本号继续解析** |
| 断网时能否判断归属 | 能 | 不能 | 能 |
| 人眼可读 | 好 | 差 | 好 |

**为什么必须有版本位**：吨袋标签贴在实物上、留样要存很久；客户改名、物料重编号、日后要加层级时，**没有版本位就意味着存量标签作废**。1 位的成本换这个，值。

### 4.2 码结构（定长 **26 位**）

```
V  T  BT  客户(4)  物料(4)  日期(6)  序1(2)  序2(3)  序3(2)  C
1  1   2     4        4        6       2       3       2    1
```

| 段 | 位 | 取值 | 说明 |
|---|---|---|---|
| **V** 版本 | 1 | `1`–`9` | 编码规则版本，改结构时 +1 |
| **T** 对象类型 | 1 | `A` `B` `C` `D` `E` | 见下表 |
| **BT** 业务类型 | 2 | `CG` / `ZG` | 客供（受托加工）/ 自购 |
| 客户 | 4 | 数字 | 客户编号 |
| 物料 | 4 | 数字 | 原料对象填原料物料号；成品对象填成品物料号 |
| 日期 | 6 | `YYMMDD` | 车次填到货日；生产/成品填生成日 |
| 序1 | 2 | 数字 | 车序 或 批序 |
| 序2 | 3 | 数字 | 袋序；非袋对象填 `000` |
| 序3 | 2 | 数字 | 保留（填 `00`） |
| **C** 校验 | 1 | 36 进制 | 前 25 位算出 |

### 4.3 对象类型与序号语义

| T | 对象 | 序1 | 序2 | 序3 | 示例 |
|---|---|---|---|---|---|
| `A` | 车次 | 车序（当日「客户+物料」流水） | `000` | `00` | `1A-CG-0001-0002-261007-03` |
| `B` | 原料吨袋 | 车序 | 袋序 | `00` | `1B-CG-0001-0002-261007-03-007` |
| `C` | 生产批 | 批序 | `000` | `00` | `1C-CG-0001-0002-261007-01` |
| `D` | 成品批 | 批序 | `000` | `00` | `1D-CG-0001-0003-261007-02` |
| `E` | 成品袋 | 批序 | 袋序 | `00` | `1E-CG-0001-0003-261007-02-015` |

- **二维码内容**：**裸串**（无分隔符，26 位定长可无歧义解析）
- **人读行**：带分隔符版（便于人工核对）
- **短副码**：标签上另印 **6 位本车/本批内流水**，供扫码枪故障时手输用
- **样品编号**：**派生串** = 父对象码 + `-S{n}`（如原料样 `1B-…-007-S1`、成品样 `1D-…-02-S1`），**不占 26 位体系**（样品是终点，不参与流转扫码）

### 4.4 序号分配规则

- 车序按「**客户 + 物料 + 到达日**」日内流水，2 位（上限 99 车/日）
- 批序按「**客户 + 物料 + 生成日**」日内流水，2 位
- ★ **预报已分配车序但车未到（空号）⇒ 跳号不回收**
  > 回收会让「同一车序在不同时间指向两辆车」，历史记录出现歧义。**空号不可怕，歧义很可怕。**
- 唯一性由数据库 UNIQUE 索引兜住，**不靠人眼**

### 5.4 取样、检测、留样

| 表 | 中文 | 关键字段 |
|---|---|---|
| `b_sample` | 样品 | sample_no(派生串 UNIQUE), sample_type(原料样/中间样/成品样), bag_id / batch_id / fg_lot_id（按类型填一）, sampled_at, sampled_by, sample_weight |
| `b_sample_retention` | 留样 | sample_id, location(如「化验室-留样柜A-第3层」), stored_at, retention_until, status(在库/已借出/已销毁), lend_records |
| `b_sample_destroy` | 销毁记录 | sample_id, destroyed_at, destroyed_by, **approved_by**, reason |
| `b_inspection` | 检测单 | inspection_no, target_type, target_id, test_date, inspector, method(全检/抽检), conclusion(合格/不合格/让步使用), defect_desc, disposition(退货/换货/让步接收/返工) |
| `b_inspection_result` | 检测结果 | inspection_id, item_id, **state(`未测` / `已测` / `不适用`)**, value_num, value_text, unit, judge, source(人工/仪器) |

## 6. 核心流程

### 6.1 收货与打码

```
客户告知车辆信息 → 收货员录【预报单】→ 系统分配车序
   → 车辆到场 → 点「到货确认」→ 生成【车次】+ 车码
   → 地磅过磅 → 录毛重/皮重 → 系统算净重
   → 录实际袋数 N → ★ 批量生成 N 个袋码 → 批量打印标签 → 逐袋贴标
   → 车/袋进入「待检」
```

- ★ **袋码在过磅确认后生成**（不按预报袋数预打），避免预报与实际不符导致作废标签。
- ★ 补打需填原因并留痕。

### 6.2 取样

```
扫码取样：扫【吨袋码】→ 生成【原料样】→ 登记留样位置/期限
扫码取样：扫【生产批码】→ 生成【中间样】
扫码取样：扫【成品批码】→ 生成【成品样】
```

- ★ **不要求每袋都有取样记录**：扫了就有，没扫就没有。**取样事实由扫码行为自然产生**，无需另建「抽检计划」。
- 取样时现场人工决定扫哪几袋（可全检、可抽检）。

### 6.3 生产与投料

```
建【生产批】→ 扫【吨袋码】投料（可跨多车多处）
   → 记作业段（班组/时间/产量）→ 一次投料产出
   → 生成【成品批】→ 批量生成【成品袋】+ 打码
   → 返工：新建批号 + 关联原批
```

### 6.4 检测

```
检测任务列表（待检的车次/吨袋/生产批/成品批）
   → 选批次 → 生成「本批次检测项清单」（从字典挑，可增删）
   → 逐项录入（三态：未测 / 已测 / 不适用）+ 上传仪器导出附件
   → 出结论（合格/不合格/让步使用）+ 处置（退货/换货/让步接收/返工）
```

- ★ 默认**待检禁用**：未出结论的原料不得投料。
- ★ 保留**「紧急放行」**通道（放行人 + 理由 + 审批人）——**与其让人绕过系统，不如给一条留痕的路**。
- ★ **让步接收须质检与使用部门双签**（沿用采购审批平台既有口径，不另造词）。

### 6.5 成品出场

```
成品批 → 装车：逐袋扫【成品袋码】归集成【出货单】
   → 出场登记（客户/车牌/司机/时间）
```

### 6.6 追溯与分享

- **正向**：车次 → 吨袋 → 投料记录 → 生产批 → 成品批 → 出货单
- **反向**：成品批 → 生产批 → 投料记录 → 吨袋 → 车次（含当时检测结果）
- **报告页**：后台选批次 → 生成**静态快照** → 上传对象存储 → 生成唯一链接
  - ★ 公网侧**只放静态文件、不连内网库** —— 内网才是真相源，公网泄露不了它没有的东西
  - ★ token 用长随机串；生命周期后台可设；**手动刷新重新生成并替换**
  - ★ 用户已定案：**不做隔离、链接可随意转发**（低成本缓解：长随机 token + 非零有效期 + 访问日志 + 页内不含其它客户数据）

### 8.3 规则

- ★ **系统管理员不自动拥有任何业务权限**（沿用采购审批平台的「最小权限」口径）—— 仅有系统角色者能进管理域，**看不到业务数据与台账**。
- 一个账号可**叠加多个角色**，权限取并集。
- ★ **「需要审批」只用于有跨部门影响的事项**：留样销毁 · 紧急放行 · 出货单撤销 · 让步接收双签。**其余更正一律不做审批，只做「填原因 + 版本链留痕」**（见 P1）—— 与其为每个更正加审批把人逼到绕路，不如让改动永远看得见。
- 「检测结果修正」不是原地改，而是**新增版本 + 作废原值**（见 P1）。
