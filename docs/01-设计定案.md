## 1. 业务背景与范围

### 1.1 业务模式

- **受托加工为主**：原料由**客户发来**，加工完成后**客户提走**，**物流由客户负责**（客户提前告知车辆信息）。
- **预留自购模式**：不排除后期自购原料加工后直接销售成品 ⇒ 用「业务类型」字段区分，**编入追踪码**。
- 原料为**吨袋包装**；**收货、投料等一切操作的最小单位都是吨袋**。

### 1.2 要解决的问题

原料从**收货 → 生产中间样 → 成品**全过程的检测数据可追踪，做到：

1. **正向追溯**：某车/某袋原料，流向了哪些成品批、哪些客户；
2. **反向追溯**：某批成品，用了哪些车/哪些袋的原料、当时检测结果如何；
3. **检测数据可信**：谁在什么时候、用什么方法、测出了什么、有没有改过。

### 1.3 一期范围（见 §9 分期）

收货预报 → 过磅 → 打码贴标 → 扫码取样 → 检测录入 → 生产投料 → 成品出场 → **追溯查询 → 对外报告分享**。

### 1.4 明确不做（本期）

| 项 | 理由 |
|---|---|
| 仪器数据直连自动采集 | 二期；前置条件是先查清各仪器是否有导出能力 |
| 离线作业与断网同步 | 磅房与化验室已有 VLAN30 网络（2.5G），无此约束 |
| 盲样检测 | 用户明确不需要 |
| 链接访问隔离 | 用户明确定案「不做隔离、可随意转发」 |
| 与采购审批平台的数据接口 | 一期零接口；口径对齐即可 |
| 生产工序节点维度 | 生产过程中只有一个取样点 |

## 2. 设计原则（贯穿全系统）

### P1 · 数据不可变：只追加，不改行

**删除与修改统一为「作废 + 新增」**：所有业务表**只 INSERT 与标记失效**，**从不 UPDATE 关键字段**。要修正 ⇒ 原行盖失效戳 + 插新行 + 互相记 `supersedes / superseded_by`。

- 代价：查询需带 `is_current = 1` 条件。
- 收益：审计追踪天然成立，「当时测的是多少」永远可回溯。

### P2 · 码携带「身份」，关系存库

追踪码只表达**「这是谁」**（哪个客户、哪个物料、哪一天的哪一车/哪一袋），**不表达「它流向谁」**。
多对多的谱系（投料关系、成品来源）**只能存关系表** —— 任何试图把谱系编进定长码的设计都会失效。

### P3 · 校验只防手输错，不防伪造

码里的校验位与版本位，**目的只是防手输错与格式自检**，**不防伪造**；防伪造靠**权限 + 审计**。

### P4 · 报表层与业务层解耦

报表/看板是**独立模块**：**只读业务表、绝不写业务表**，可单独替换与调整，不影响核心表结构与录入流程。

## 3. 术语与对象模型

```
客户 customer
   │
   └─ 预报单 arrival_notice ──→ 车次 truck_lot（到货事件）
                                    │
                                    ├─ 吨袋 bag ×N          ← 操作最小单位
                                    │     └─ 原料样 sample（扫吨袋码取样）
                                    │
                                    └─ 投料 feed_record ×N ──┐
                                                             ↓
                                              生产批 production_batch
                                                ├─ 作业段 batch_operation ×N（班组/时间）
                                                ├─ 中间样 sample
                                                └─ 成品批 fg_lot
                                                      ├─ 成品袋 fg_bag ×N
                                                      ├─ 成品样 sample
                                                      └─ 出货 shipment ──→ 客户
```

| 对象 | 说明 | 关键点 |
|---|---|---|
| **客户** | 委托方 | 4 位数字编号，全局唯一 |
| **物料** | 原料/成品统一建模 | 由「原料组成 × 原料类型」两个维度组合而成 |
| **车辆** | 车牌号主数据 | 长期存在，记录常用司机/电话 |
| **预报单** | 客户提前告知的车辆信息 | 由收货员录入 |
| **车次** | 一次到货事件 | ★ 同一辆车一天来两趟 = 两个车次 |
| **吨袋** | 车内的一袋原料 | ★ 收货/投料的最小单位，逐袋贴码 |
| **生产批** | 一次投料产出 | 可跨班组（记多段作业）；可多车合并 |
| **成品批** | 生产批的产出 | 可拆分为多批 |
| **成品袋** | 成品吨袋 | 出场逐袋扫码 |
| **样品** | 原料样/中间样/成品样 | 留样是一等公民，管位置与期限 |

### 3.1 谱系关系（多对多，存库不存码）

- **车次 ⇄ 生产批**：**N:M**（一车可拆多批、多车可并入一批）
- **生产批 → 成品批**：1:N
- **成品批 → 出货**：N:M

### 3.2 称重口径（重要限制）

**只有地磅称整车，不逐袋过磅**。

- `车次` 记 **毛重 / 皮重 / 净重**；
- `吨袋` 的重量 = **车净重 ÷ 袋数**，即 **摊算值**；
- ★ **系统必须显式标记 `weight_is_allocated = true`**，追溯报告写作「**约 X 吨**」。

> 理由：客户日后追问「这袋料到底多少吨」，必须答得出这个数**来自摊算而非实测**。不标记的话，半年后无人记得它是估的。

## 4. 追踪码规则

> ★★ **详细规范已独立成文 → [`02-追踪码规则.md`](02-追踪码规则.md)**：逐位说明 · 五种对象示例（含**已核算过的校验位**）· 校验算法与强度 · 解析规则 · 版本演进 · 边界异常。
> ★ **本规则 v1 已冻结**（用户 2026-10-08 确认「编码暂时这样没问题」），作为 mimo 实现依据。
> **本节只保留结论与要点。**

### 4.1 方案选型

采用 **「结构化 + 编码版本位 + 校验位」**（方案丙）。核心取舍：

| | 甲 纯结构化 | 乙 短流水 | **丙 结构化+版本位（选定）** |
|---|---|---|---|
| 编码体系变更（客户/物料重编号、增删层级） | ★ 存量标签全废 | 不受影响 | ★ **老码按版本号继续解析** |
| 断网时能否判断归属 | 能 | 不能 | 能 |
| 人眼可读 | 好 | 差 | 好 |

**为什么必须有版本位**：吨袋标签贴在实物上、留样要存很久；客户改名、物料重编号、日后要加层级时，**没有版本位就意味着存量标签作废**。1 位的成本换这个，值。

### 4.2 码结构（定长 **27 位** = 裸串 26 + 校验 1）

```
V  T  BT  客户(4)  物料(4)  日期(6)  序1(2)  序2(3)  序3(3)  C
1  1   2     4        4        6       2       3       3    1
```

| 段 | 位 | 取值 | 说明 |
|---|---|---|---|
| **V** 版本 | 1 | `1`–`9` | 编码规则版本；改结构时 +1，**老码按老版本继续解析** |
| **T** 对象类型 | 1 | `A` `B` `C` `D` `E` | 见 §4.3 |
| **BT** 业务类型 | 2 | `CG` / `ZG` | 客供（受托加工）/ 自购；★ 自购时客户段填保留值 `0000` |
| 客户 | 4 | 数字 | 客户编号 |
| 物料 | 4 | 数字 | ★ **原料对象填原料物料号；成品对象填成品物料号**（同一链内一致） |
| 日期 | 6 | `YYMMDD` | **链根日期**：原料链＝到货日；成品链＝生产批创建日 |
| 序1 | 2 | 数字 | 第 1 层：车序 / 生产批序 |
| 序2 | 3 | 数字 | 第 2 层：袋序 / 成品批序；无此层填 `000` |
| 序3 | 3 | 数字 | 第 3 层：成品袋序；★ **原料链恒 `000`**（原料链只有 2 层） |
| **C** 校验 | 1 | `0-9A-Z` | 前 26 位算出（算法见 [`02`](02-追踪码规则.md) §7） |

### 4.3 对象类型与「三层序」的对应

★★ **关键规则：序段表达的是「从链根到本对象」的完整路径，不是本对象自己的流水。**

| T | 对象 | 序1 | 序2 | 序3 | 层级深度 | 示例（人读行，此处省去校验位） |
|---|---|---|---|---|---|---|
| `A` | 车次 | 车序 | `000` | `000` | 1 | `1A-CG-0001-0002-261007-03` |
| `B` | 原料吨袋 | 车序 | 袋序 | `000` | 2 | `1B-CG-0001-0002-261007-03-007` |
| `C` | 生产批 | 批序（按**产出成品物料**编） | `000` | `000` | 1 | `1C-CG-0001-0003-261007-03` |
| `D` | 成品批 | ★ **来源生产批的批序** | 该生产批内第几个成品批 | `000` | 2 | `1D-CG-0001-0003-261007-03-002` |
| `E` | 成品吨袋 | ★ **来源生产批的批序** | 成品批序 | 袋序 | 3 | `1E-CG-0001-0003-261007-03-002-015` |

- ★★ **为什么 `D`/`E` 的序1 必须是「来源生产批序」而不是自己的流水**：只有这样，**成品袋码才自带完整祖先链** —— 扫一袋成品，从码上直接读出它属于哪个生产批、哪个成品批，**不用查库**。这正是「码携带身份」的价值（原则 P2）。
- ★ **原料链只有 2 层，所以原料链的序3 恒为 `000`** —— 这不是「没用的死位」，而是「**层级深度只有 2**」的正常表达；该段**有明确定义**，与「未定义、可随便填」是两回事。
- ★ **`C`（生产批）的物料段填产出成品物料**，不是投入原料物料 —— 这样 `C`/`D`/`E` 三者同链物料段一致，序段才能层层引用。**投入了什么料，查投料记录。**

### 4.4 三种「码面」

- **二维码内容**：**裸串 27 位**（无分隔符，定长可无歧义解析）
- **人读行**：带分隔符的全码，与裸串**严格同构**（可双向转换）
- ★ **不设短副码**：手输走「**先选父对象，再输本层序号**」通道（引入"第二套编号"的维护成本与混淆风险不值得）
- **样品编号**：**派生串** = 父对象码 + `-` + 角色码 + 2 位序号，角色码 `I`份样 / `C`大样 / `R`保留样 / `A`仲裁样（见 §6.2）；**不占 27 位体系**

### 4.5 序号分配规则

- 车序按「**客户 + 原料物料 + 到达日**」日内流水，2 位（上限 99 车/日）
- 批序按「**客户 + 成品物料 + 生产批创建日**」日内流水，2 位
- ★ **空号跳号不回收**（预报分配了车序但车未到）—— 回收会让「同一车序在不同时间指向两辆车」
- ★ **并发取号必须串行化**（同一事务内取号），**禁止"先查最大值再 +1"**；唯一性由数据库 UNIQUE 索引兜住，**不靠人眼**
- ★ **超限不自动进位** —— 报错由人决策（自动加宽段位会破坏定长，整套解析失效）
- **改预报不改车序**（否则与已打印标签对不上）

### 5.1 主数据

|---|---|---|
| `m_customer` | 客户 | code(4), name, short_name, contact, phone, is_internal, external_id |
| `m_composition` | 原料组成 | code, name（荆门焦、长岭焦…） |
| `m_material_type` | 原料类型 | code, name（煅后焦、半煅焦…） |

| `m_test_item` | 检测项目 | code, name, unit, method, value_type(数值/文本/枚举), lower_limit, upper_limit, decimals, sort |

### 5.2 收货与打码

|---|---|---|
| `b_arrival_notice` | 预报单 | notice_no, customer_id, material_id, vehicle_id, driver, phone, eta, est_bag_count, biz_type, status(预报/已到货/已取消/空号), created_by |
| `b_truck_lot` | 车次 | **code**(27位 UNIQUE), notice_id, customer_id, material_id, vehicle_id, driver, phone, biz_type, arrive_date, arrive_at, gross_weight, tare_weight, net_weight, bag_count, status, operator |
| `b_bag` | 原料吨袋 | **code**(27位 UNIQUE), truck_lot_id, bag_seq, weight_allocated, **weight_is_allocated**, status(在库/已投料/已退回/留样中/**作废**) |

| `b_obj_void` | **通用作废记录** | entity(表名), entity_id, reason, voided_by, voided_at, approved_by（★ 袋/批/单据的作废统一走这张表；**作废码永久不重用**） |

### 5.3 生产与谱系

| 表 | 中文 | 关键字段 |
|---|---|---|
| `b_production_batch` | 生产批 | **code**(27位 UNIQUE), customer_id, **input_material_id**(投入), **planned_output_material_id**(计划产出，用于批号编排), date, status ← ★ **不含实际产出**（见下边界说明） |
| `b_batch_operation` | 作业段 | batch_id, seq, team_id, operator, start_at, end_at, output_weight（★ 承载「跨班组」） |
| **`b_feed_record`** | **投料记录** | **batch_id, bag_id, feed_weight, fed_at, operator** ← ★ **谱系表的承重墙** |
| `b_fg_lot` | 成品批 | **code**(27位 UNIQUE), **batch_id(来源生产批)**, customer_id, **output_material_id**, pack_spec, qty_bag, net_weight, produced_at, status ← ★ **唯一的实际产出记录** |
| `b_fg_bag` | 成品袋 | **code**(27位 UNIQUE), fg_lot_id, bag_seq, weight_allocated, weight_is_allocated, status(在库/已出厂) |
| `b_rework` | 返工关联 | new_batch_id, src_batch_id, reason（★ 返工用**新批号 + 关联原批**） |

> ★★ **生产批 与 成品批 的边界（消除"两份真相"）**：

| | **生产批 `b_production_batch`** | **成品批 `b_fg_lot`** |
|---|---|---|
| 语义 | **投料与作业的「过程单元」**（干了什么） | **产出的「可交付分段」**（产出了什么） |
| 承载 | 投入物料 · 投料记录 · 作业段（班组/工时） | **产出物料 · 包装规格 · 袋数 · 净重 · 产出时间** |
| 数量 | **1 生产批 → N 成品批（N ≥ 1）** | 常见 N = 1；拆分的典型理由是**包装规格不同**或**分时段产出** |
| 码 | `C` | `D`（序1＝来源生产批序 · 序2＝本批内第几个） |

> ★ **实际产出只在 `b_fg_lot` 记一次**；`b_production_batch` 只留「**计划**产出物料」用于批号编排与排产。
> **理由**：产出物料与产出重量若同时存在于两表，就是典型的「两份真相」—— 迟早对不上，且没人说得清哪个对。

### 5.4 取样、检测、留样

> ★★ **模型依据国标取样路径：`份样 → 大样 → 检测`，且检测样与保留样物理分开。**
> - **GB/T 1997-2008**：全面取样按**份样**取；制样时「**缩分成两等份，一份测定、一份作保留样**」
> - **GB/T 2007.1-1987**：批量大时按取样单元分取，**结果按质量加权平均作为交货批检验结果**
> - 行业实际：常平分三份 —— **检测 · 保留备查 · 仲裁**

| 表 | 中文 | 关键字段 |
|---|---|---|
| `b_sample_group` | **取样组（大样）** | group_no, target_type(车次/生产批/成品批), target_id, sampled_at, sampled_by, sample_count(份样数) |
| `b_sample` | **样品** | sample_no(派生串 UNIQUE), **role(`份样`/`大样`/`保留样`/`仲裁样`)**, group_id, bag_id / batch_id / fg_lot_id（按类型填一）, sampled_at, sampled_by, sample_weight |
| `b_sample_retention` | 留样 | sample_id, location(如「化验室-留样柜A-第3层」), stored_at, retention_until, status(在库/已借出/已销毁) |
| `b_sample_lend` | **留样借还记录** | sample_id, lent_at, lent_to, returned_at, purpose（★ 独立表，不用 JSON 字段 —— 与 P1 冲突） |
| `b_sample_destroy` | 销毁记录 | sample_id, destroyed_at, destroyed_by, **approved_by**, reason |
| `b_inspection` | 检测单 | inspection_no, target_type, target_id, **group_id（★ 检测挂「大样」）**, test_date, inspector, method(全检/抽检), conclusion(`合格`/`不合格`/**`CONCESSION`**), defect_desc, **authorized_by（★ 让步授权人，ISO 9001 8.7.2 强制）**, disposition(退货/换货/让步接收/返工), is_recheck, recheck_of, ★ **`cust_notified_at` / `cust_contact` / `cust_channel`（让步接收时必填：何时 / 告知谁 / 什么渠道）, `cust_confirm_file_id`（客户书面确认，可选）** |
| `b_inspection_result` | 检测结果 | inspection_id, item_id, **state(`未测` / `已测` / `不适用`)**, value_num, value_text, unit, judge, source(人工/仪器) |
| `b_inspection_file` | 检测附件 | inspection_id, file_name, file_path, file_type, uploaded_by |

> ★★ **检测挂「大样」，不挂袋**：一车 30 袋 → 逐袋取**份样**（每袋另留**保留样**）→ 合并成**大样** → **检测只做大样**。
> ⇒ **整车结论 = 大样的检测结果**，天然成立，**不需要"袋级结果汇总规则"**。
> ⇒ ★ **整车/整批结论按 GB/T 2007.1 的质量加权平均**（散装交货批）或 **GB/T 2828.1 的 AQL 判定**（计数型，用接收数 Ac / 拒收数 Re）；**不是"一票否决"**。
> ★ **让步术语规范化为 `CONCESSION`**（GB/T 19000 / ISO 9001 8.7 用语），界面显示沿用「让步接收」。
> **★ 三态不可合并**：「未测」是**待办**，「不适用」是**结论**。
> **★ 批次检测项清单＝`b_inspection_result` 的行集合**（含「未测」行），不另建表；**一旦有结果录入，只能加项、不能删已有结果的项**。

> **★ 三态不可合并**：「未测」是**待办**，「不适用」是**结论**。都存成空 ⇒ 永远分不清「忘了测」与「不用测」。
> **★ 批次检测项清单一旦有结果录入，只能加项、不能删已有结果的项** —— 否则会出现「结果还在、项目没了」的孤儿数据。

## 6. 核心流程

### 6.1 收货与打码

```
客户告知车辆信息 → 收货员录【预报单】→ 系统分配车序
   → 车辆到场 → 点「到货确认」→ 生成【车次】+ 车码
   → 地磅过磅 → 录毛重/皮重 → 系统算净重
   → 录实际袋数 N → ★ 批量生成 N 个袋码 → 批量打印标签 → 逐袋贴标
   → 车/袋进入「待检」
```

- ★ **袋码在过磅确认后生成**（不按预报袋数预打），避免预报与实际不符导致作废标签。
- ★ 补打需填原因并留痕。

### 6.2 取样（按国标：份样 → 大样 → 检测）

```
① 逐袋扫码取样（扫【吨袋码】）→ 每袋生成 1 个【份样】+ 1 个【保留样】
② 现场决定是否合并 → 生成【取样组 / 大样】→ 把若干【份样】并入
③ 中间样 / 成品样：扫【生产批码】/【成品批码】→ 生成【份样】+【保留样】
④ 登记保留样的位置与保留期限
```

- ★ **不要求每袋都有取样记录**：扫了就有，没扫就没有。**取样事实由扫码行为自然产生**，无需另建「抽检计划」。
- ★ **检测只对大样做**（见 §5.4）—— 所以在系统里「样品」与「被检测的对象」是**两个层级**。
- ★ **保留样与检测样物理分开**（国标要求）：**保留样单独跟踪位置与到期**，不因检测完成而销毁。
- **样品编号**：`父对象码 + "-" + 角色码 + 2 位序号`，角色码 `I`份样 / `C`大样 / `R`保留样 / `A`仲裁样。
  例：`1B-CG-0001-0002-261007-03-007-R01` ＝ 该吨袋的 1 号保留样。
- ★ **仲裁样**：客户对结果有异议时启封（见 §6.4 复检）。

### 6.3 生产与投料

```
建【生产批】→ 扫【吨袋码】投料（可跨多车多处）
   → 记作业段（班组/时间/产量）→ 一次投料产出
   → 生成【成品批】→ 批量生成【成品袋】+ 打码
   → 返工：新建批号 + 关联原批
```

### 6.4 检测

```
检测任务列表（待检的车次 / 生产批 / 成品批）
   → 选对象 → 挂到它的【大样】上 → 生成「本批次检测项清单」（从字典挑，可增删）
   → 逐项录入（三态：未测 / 已测 / 不适用）+ 上传仪器导出附件
   → 出结论（合格 / 不合格 / 让步）+ 处置（退货 / 换货 / 让步接收 / 返工）
   → 复检：在原批次上发起新检测单（is_recheck + recheck_of），不覆盖原结果
```

- ★ **默认「待检禁用」：未出结论的原料不得投料**；★ **放行单位是「车次」，不是「袋」**。
- ★ **整车/整批结论**：按 GB/T 2007.1 的**质量加权平均**，或 GB/T 2828.1 的 **AQL 判定**（接收数 Ac / 拒收数 Re）—— **不是"一票否决"**。
- ★ 保留**「紧急放行」**通道（放行人 + 理由 + 审批人）——**与其让人绕过系统，不如给一条留痕的路**。
- ★ **让步接收须质检与使用部门双签**；★ 并**强制记录「授权人」**（ISO 9001 8.7.2 强制要求）。
- ★ **过滤：不合格 → 退货 → 退车登记 → 车次转「已退货」→ 该车所有袋码作废**（写入 `b_obj_void`，码永久不重用）。
- ★★ **让步接收料所产出的成品：对外报告页【不披露】**（用户定案：让步接收**事先已与客户商量好**，成品无需再声张）；★ **内部批次档案一律显著标注**，便于内部追溯。
- ★★ **让步接收须填「客户沟通记录」**（何时 / 告知谁 / 什么渠道，**必填**）＋ **客户书面确认附件（可选）** —— 用户定案（D22）。
  ★ 理由：让步既然「**事先已与客户商量好**」，那「**何时跟谁说的**」就是这次动作本身的组成部分，记录它只花十秒；而「客户愿不愿给书面」不由我们决定，因此附件**不强制**。
### 6.5 成品出场

```
成品批 → 装车：逐袋扫【成品袋码】归集成【出货单】
   → 出场登记（客户/车牌/司机/时间）
```

### 6.6 追溯与分享

- **正向**：车次 → 吨袋 → 投料记录 → 生产批 → 成品批 → 出货单
- **反向**：成品批 → 生产批 → 投料记录 → 吨袋 → 车次（含当时检测结果）
- **报告页**：后台选批次 → 生成**静态快照** → ★ **一期落本地静态目录（复用服务器已有的 Caddy 供外网访问），二期再切云厂商对象存储** → 生成唯一链接
  - ★ 公网侧**只放静态文件、不连内网库** —— 内网才是真相源，公网泄露不了它没有的东西
  - ★ token 用长随机串；生命周期后台可设；**手动刷新 = 生成新 token 新链接**（避免"同一个 URL 内容悄悄变了"）
  - ★ 用户已定案：**不做隔离、链接可随意转发**（低成本缓解：长随机 token + 非零有效期 + 访问日志 + 页内不含其它客户数据）

## 8. 权限模型与配置

> ★★ **权限不写死在代码里** —— 由「权限点字典 × 角色 × 授权 × 用户角色绑定」**四张表**驱动，在 **系统管理 → 权限配置** 页面后台维护。

### 8.0 权限模型（数据驱动）

**权限 = 角色 × 权限点 × 授权级别**。

| 表 | 内容 | 可维护性 |
|---|---|---|
| `s_permission_point` | **权限点字典**：`code` · `module` · `name` · `levels`（该点支持的级别集合） · `scope_kind`（预留） · `sort` · `is_system` · `status` | ★ **由代码注册（迁移/种子）**，后台**只能启用/停用，不可新增删除** |
| `s_role` | **角色**：`code` · `name` · `is_system` · `sort` · `status` | 后台**可新增**；**内置角色不可删除** |
| `s_role_permission` | **授权**：`role_code` × `point_code` → `level`，`UNIQUE(role_code, point_code)` | 后台可改 |
| `s_user_role` | **用户角色绑定**：`open_id` × `role_code`，`UNIQUE(open_id, role_code)` | 后台可改；★ 一人可叠加多角色 |

**授权级别**（4 级 + 无）：`ALL` 全（增/改/停） · `READ` 只读 · `INIT` 仅发起 · `APPROVE` 仅审批 · `NONE` 无。

> 每个权限点**自己声明支持哪些级别**（例：「标签打印」只支持 `ALL / NONE`；「紧急放行」拆成「发起」「审批」两点，各支持 `ALL / NONE`）。后台配置时选的是「**这个角色在这个点上取哪一级**」。

### 8.0.1 ★★ 三条硬约束（防止配置与代码脱节）

1. **权限点字典由代码注册，后台不可增删。**
   后台凭空新建一个权限点 ⇒ 造出「**假权限**」（配了却没人执行，同族：`immutable`、写了没人读的判据）；反之，代码里引用字典外的权限点 ⇒ 「**没声明却保护了**」。
2. **门禁两项**（纳入必绿项）：
   - ① **每个权限点必须至少被一处代码消费** —— 防「配了没用」；
   - ② **每个受保护入口必须引用已登记的权限点常量**（**禁止裸写字符串**）—— 防「字典改了、代码没跟上」。
3. ★★ **防锁死：`系统管理员`角色的管理域权限不可被后台修改或剥夺**，且系统保持**至少一个管理员账号**；另提供**环境变量引导**兜底（同采购平台的 `JX_BOOTSTRAP_SYS_ADMIN_OPEN_ID` 口径）。
   > 否则一次误配置就会把所有人挡在门外，且**没有任何界面能改回来**。

### 8.0.2 边界

- **行级 / 列级权限：一期不做。** 现场 4–5 个角色，按角色分权已足够；`s_permission_point` 预留 `scope_kind` 字段位，二期需要时再启用。
- **权限变更审计**：所有授权改动写入统一审计日志（谁 / 何时 / 把哪个角色的哪个权限点 / 从哪级改到哪级）。

| 操作 | 系统管理员 | 管理层/销售 |
|---|---|---|

| 编码规则版本配置 | 全 | — |

### 8.3 种子取值规则

- ★ **系统管理员不自动拥有任何业务权限**（沿用采购审批平台的「最小权限」口径）—— 仅有系统角色者能进管理域，**看不到业务数据与台账**。
- 一个账号可**叠加多个角色**，权限取并集。
- ★ **「需要审批」只用于有跨部门影响的事项**：留样销毁 · 紧急放行 · 出货单撤销 · 让步接收双签。**其余更正一律不做审批，只做「填原因 + 版本链留痕」**（见 P1）—— 与其为每个更正加审批把人逼到绕路，不如让改动永远看得见。
- 「检测结果修正」不是原地改，而是**新增版本 + 作废原值**（见 P1）。
